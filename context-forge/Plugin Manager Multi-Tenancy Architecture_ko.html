    플러그인 매니저 멀티테넌시 아키텍처

    원문: https://github.com/IBM/mcp-context-forge/blob/main/docs/architecture-plugin-multi-tenancy.md · 작성일: 2026-10-30

    개요

    플러그인 하위 시스템은 공유 TenantPluginManagerFactory를 통해 컨텍스트 범위 격리를 지원합니다. 확인된(resolved) 각 컨텍스트는 독립적으로 병합된 플러그인 설정을 가진 자체 TenantPluginManager 인스턴스를 받으며, 기본 __global__ 컨텍스트는 컨텍스트를 인식하지 않는 호출 지점을 계속 처리합니다.

    팩토리는 의도적으로 컨텍스트에 무관(context-agnostic)하게 설계되었습니다. get_manager()에 전달하는 식별자는 가상 서버, 테넌트, 도구, 사용자 또는 다른 범위 지정 키를 나타낼 수 있습니다. 팩토리는 이 값을 해석하지 않고, 다음 용도로만 사용합니다.

    • 캐시된 기존 매니저 조회
    • get_config_from_db(context_id)를 통한 선택적 설정 오버라이드 가져오기
    • TenantPluginManager 생성 및 초기화
    • 재사용을 위한 결과 캐싱

    현재 게이트웨이 연결 구조에서 주요 런타임 사용 방식은 다음과 같습니다.

    • 공유/전역 플러그인 실행에는 get_plugin_manager() 또는 get_plugin_manager("__global__")
    • 도구, 프롬프트, 리소스 같은 서비스의 서버 범위 실행에는 get_plugin_manager(server_id)

    플러그인 설정 생명주기

    시작 시: YAML이 단일 진실 공급원

    플러그인은 반드시 시작 시점에 YAML 설정 파일에 선언해야 합니다. YAML은 어떤 플러그인이 존재하는지와 각 플러그인의 기본 mode, priority, 플러그인별 config 키를 정의합니다. 이 기본 설정은 TenantPluginManagerFactory가 한 번 로드하며 런타임에는 변경할 수 없습니다 — 재시작하지 않고는 바꿀 수 없습니다.

    plugins/config.yaml
  └─ plugin A  (mode: enforce, priority: 10, config: {...})
  └─ plugin B  (mode: permissive, priority: 20, config: {...})

    YAML에 나열된 플러그인만 컨텍스트에 참여합니다. 런타임에 완전히 새로운 플러그인을 도입하는 메커니즘은 없습니다.

    런타임: PluginConfigOverride를 통한 컨텍스트별 오버라이드

    각 컨텍스트(예: 가상 서버)마다 팩토리는 기본 YAML 설정 위에 PluginConfigOverride 객체 목록을 적용할 수 있습니다. 오버라이드로 할 수 있는 일은 다음과 같습니다.

    • 플러그인의 mode 변경(예: 특정 서버에서 permissive를 enforce로 격상)
    • 플러그인의 priority 변경(체인 안의 실행 순서 재배치)
    • 플러그인 config 딕셔너리의 키 추가 또는 교체(세부 사용자 정의 설정)

    오버라이드는 추가적이고 선택적입니다. 오버라이드에 명시적으로 설정한 필드만 적용되고, 나머지는 모두 YAML 기본값을 상속합니다. 오버라이드 목록에 없는 플러그인은 그대로 사용됩니다.

    PluginConfigOverride
  └─ name: "plugin A"
  └─ mode: permissive       # overrides YAML value for this context
  └─ config: {threshold: 5} # merged on top of base config

    가져오기 훅: get_config_from_db

    get_config_from_db(context_id)는 컨텍스트 식별자를 영구 저장소에서 가져온 PluginConfigOverride 객체 목록으로 변환하는 확장 지점입니다.

    기본 구현은 항상 None(오버라이드 없음)을 반환합니다. 서브클래스는 이 메서드를 오버라이드해 데이터베이스나 다른 저장소에서 context_id에 연결된 컨텍스트별 플러그인 설정을 조회합니다.

    반환된 오버라이드는 _merge_tenant_config로 바로 전달됩니다. 이 메서드는 기본 설정의 플러그인 목록을 순회하며 각 오버라이드를 적용합니다. 플러그인별 config 딕셔너리는 얕은 병합(shallow merge)되며(오버라이드 키가 우선), 선택 필드인 mode와 priority는 값이 있으면 기본값을 대체합니다. 그 결과로 만들어진 새 Config 객체로 해당 컨텍스트의 격리된 TenantPluginManager를 구성합니다.

    요약하면, get_config_from_db는 팩토리와 영속성 계층 사이의 이음매입니다. 컨텍스트별 플러그인 설정을 동적으로 만들려면 이 메서드를 오버라이드하세요.

    flowchart TD
    Y["YAML config file\n(loaded at startup, immutable)"]
    DB["Persistence layer\n(DB, config store, etc.)"]
    H["get_config_from_db(context_id)\n[override this in subclass]"]
    O["list[PluginConfigOverride]\n(mode / priority / config keys)"]
    M["_merge_tenant_config()"]
    C["Merged Config\n(per-context)"]
    T["TenantPluginManager\n(per-context instance)"]

    Y --> M
    DB --> H
    H --> O
    O --> M
    M --> C
    C --> T

    아키텍처 요약

    flowchart TD
    APP["Application lifespan\n(mcpgateway.main)"]
    F["TenantPluginManagerFactory\n(singleton, holds base YAML config)"]
    G["TenantPluginManager\ncontext = '__global__'\n(backward-compat global manager)"]
    S1["TenantPluginManager\ncontext = 'server-id-1'"]
    S2["TenantPluginManager\ncontext = 'server-id-2'"]
    DB["get_config_from_db(context_id)\n(fetch per-context overrides)"]
    YAML["plugins/config.yaml\n(base plugin config)"]

    APP -->|"init_plugin_manager_factory()"| F
    YAML -->|"loaded once at startup"| F
    F -->|"eager: get_manager()"| G
    F -->|"lazy: get_manager(server_id)"| S1
    F -->|"lazy: get_manager(server_id)"| S2
    F <-->|"override fetch"| DB

    주요 컴포넌트

    • PluginManager: 인스턴스 간 상태를 공유하는 레거시 Borg 방식 매니저입니다.
    • TenantPluginManager: Borg 동작을 끄고 인스턴스마다 완전히 독립된 상태를 유지하는 PluginManager 서브클래스입니다.
    • TenantPluginManagerFactory: 컨텍스트별 매니저를 위한 비동기 안전(async-safe) 캐시/팩토리입니다.
    • get_plugin_manager(): mcpgateway.plugins.framework.__init__에 있는 전역 접근자로, 플러그인이 활성화되어 있으면 싱글턴 팩토리에서 컨텍스트 매니저를 반환합니다.

    현재 런타임 동작

    시작

    시작 시 mcpgateway.main.lifespan()은 다음을 수행합니다.

    1. 설정되어 있으면 플러그인 하위 시스템을 활성화합니다.
    2. 다음 값으로 전역 TenantPluginManagerFactory를 초기화합니다.
      • YAML 설정 경로
      • 플러그인 타임아웃
      • 훅 페이로드 정책
      • 선택적 관측성(observability) 프로바이더
    3. await get_plugin_manager()를 호출해 기본 __global__ 매니저를 확보합니다.
    4. 그 밖의 컨텍스트별 매니저는 처음 사용할 때 지연 생성되도록 남겨 둡니다.

    즉, 팩토리는 즉시 초기화되지만 대부분의 테넌트/서버 매니저는 필요할 때 초기화됩니다.

    요청 시점 확인

    컨텍스트 범위 지정을 지원하는 서비스는 get_plugin_manager(server_id)를 호출해 다음 중 하나를 받습니다.

    • 캐시된 TenantPluginManager
    • 해당 컨텍스트용으로 새로 생성하고 초기화한 매니저

    컨텍스트 ID를 제공하지 않는 호출 지점은 계속 기본 전역 매니저를 사용합니다.

    핵심 타입

    PluginManager

    PluginManager는 여전히 기본 구현이며, 지금도 Borg 패턴을 사용합니다.

    속성현재 동작
    상태 모델인스턴스 간 공유되는 __dict__
    주요 역할레거시/전역 호환성
    초기화YAML 설정을 로드하고 레지스트리/실행기 상태를 공유
    초기화(reset) 경로PluginManager.reset()이 공유된 Borg 상태를 지움

    TenantPluginManager

    TenantPluginManager는 PluginManager의 공개 API를 상속하지만 Borg 초기화 경로를 우회합니다.

    속성현재 동작
    상태 모델인스턴스마다 독립
    설정 출처Config 객체 또는 YAML 경로
    레지스트리매니저마다 전용 PluginInstanceRegistry
    실행기매니저마다 전용 PluginExecutor
    잠금매니저마다 자체 비동기 초기화/종료 잠금

    enable_borg()는 아무 동작도 하지 않도록 오버라이드되어 있으므로, 테넌트 매니저는 상태를 공유하지 않습니다.

    TenantPluginManagerFactory

    mcpgateway/plugins/framework/manager.py에 정의되어 있습니다.

    메서드현재 동작
    get_manager(context_id=None)캐시된 매니저를 반환하거나 새로 만듦. 기본값은 __global__
    _build_manager(context_id)오버라이드를 가져오고, 설정을 병합하고, 매니저를 초기화하고, 캐시 항목을 교체
    _merge_tenant_config(overrides)기본 YAML 설정 위에 플러그인별 오버라이드 값을 적용
    reload_tenant(context_id)캐시된 매니저를 제거하고 다시 만든 뒤, 이전 매니저를 종료
    shutdown()진행 중인 생성을 취소하고 캐시된 모든 매니저를 종료
    get_config_from_db(context_id)확장 훅. 기본 구현에서는 None을 반환 — DB 기반 오버라이드를 사용하려면 서브클래스를 만드세요

    접근자 계층

    공개 접근자는 mcpgateway/plugins/framework/__init__.py에 있습니다.

    함수현재 동작
    enable_plugins(toggle)플러그인 하위 시스템을 전역으로 활성화하거나 비활성화
    init_plugin_manager_factory(...)시작 중에 싱글턴 팩토리를 명시적으로 생성
    get_plugin_manager(server_id="__global__")플러그인이 활성화되어 있고 팩토리가 존재하면 컨텍스트 매니저를 반환
    shutdown_plugin_manager_factory()팩토리를 종료하고 싱글턴 참조를 지움
    reset_plugin_manager_factory()테스트용으로 싱글턴 참조를 지움

    중요한 참고 사항

    접근자는 팩토리를 지연 초기화하지 않습니다. 시작 중에 팩토리가 초기화되지 않았다면 get_plugin_manager()는 None을 반환합니다.

    설정 병합 모델

    각 컨텍스트는 기본 YAML 플러그인 설정에서 시작하며, 선택적으로 get_config_from_db(context_id)가 반환한 PluginConfigOverride 객체 목록을 적용합니다.

    기본 설정에 이미 있는 플러그인만 병합에 참여합니다. 런타임에 새 플러그인을 도입하는 메커니즘은 없으며, YAML이 정식 플러그인 레지스트리입니다.

    일치하는 각 플러그인에 대해:

    • config는 얕은 병합됩니다: {**base.config, **override.config} — 오버라이드 키가 우선합니다.
    • mode는 오버라이드에 값이 있을 때만 교체됩니다.
    • priority는 오버라이드에 값이 있을 때만 교체됩니다.

    오버라이드 목록에 없는 플러그인은 변경되지 않습니다. 오버라이드로 None을 전달하면 기본 설정을 그대로 사용한다는 뜻입니다.

    flowchart LR
    B["Base YAML config\n(plugin A, plugin B, plugin C)"]
    O["PluginConfigOverride list\nfrom get_config_from_db(context_id)"]
    M["_merge_tenant_config()"]
    R["Merged context Config\n(used to build TenantPluginManager)"]

    B -->|"all plugins"| M
    O -->|"selective overrides\nmode / priority / config keys"| M
    M --> R

    동시성 모델

    매니저 생성은 _inflight를 통해 컨텍스트별로 중복 제거됩니다.

    여러 코루틴이 같은 컨텍스트 매니저를 동시에 요청하면:

    1. 첫 번째 호출자가 잠금을 획득하고 _build_manager(context_id)를 asyncio.Task로 생성합니다.
    2. 작업이 _inflight[context_id]에 저장되고 잠금이 해제됩니다.
    3. 이후에 잠금을 획득한 호출자는 기존 작업을 찾아 await합니다.
    4. 작업이 완료되면 _build_manager가 잠금을 잡은 상태에서 결과를 _managers에 저장합니다.
    5. get_manager는 await 이후 _managers를 다시 확인해, 동시에 실행된 reload_tenant가 일으킨 교체를 반영합니다.
    6. 작업은 finally 블록에서 _inflight에서 제거됩니다.

    이렇게 하면 컨텍스트마다 한 번에 하나의 초기화 경로만 실행되고, 동시에 호출한 쪽들은 중복 매니저를 만들려고 경쟁하는 대신 결과를 공유합니다.

    sequenceDiagram
    participant C1 as Caller 1
    participant C2 as Caller 2
    participant F as Factory (lock)
    participant T as _build_manager task

    C1->>F: get_manager("server-1")
    F->>F: cache miss → create task
    F->>T: asyncio.create_task(_build_manager)
    F-->>C1: release lock, await task
    C2->>F: get_manager("server-1")
    F->>F: cache miss → inflight task found
    F-->>C2: release lock, await same task
    T-->>F: initialize manager, store in _managers
    T-->>C1: return manager
    T-->>C2: return same manager

    리로드와 종료 시맨틱

    리로드

    reload_tenant(context_id):

    1. 잠금을 획득하고 해당 컨텍스트의 캐시된 매니저를 제거합니다.
    2. 같은 컨텍스트에 대해 진행 중인 생성 작업이 있으면 취소합니다.
    3. 새 _build_manager 작업을 만들어 _inflight에 저장합니다.
    4. 잠금을 해제하고, 잠금 밖에서 이전 매니저를 종료합니다.
    5. 새 작업을 await하고 다시 만든 매니저를 반환합니다.

    종료

    shutdown():

    1. 잠금을 잡은 상태에서 캐시된 매니저와 진행 중인 작업의 스냅샷을 만듭니다.
    2. 두 캐시를 원자적으로 비웁니다.
    3. 진행 중인 모든 작업을 취소합니다.
    4. 작업이 끝날 때까지 await합니다(예외 수집).
    5. 캐시된 각 매니저를 종료합니다.

    이렇게 하면 활성 매니저 인스턴스를 남기지 않고 질서 있게 정리할 수 있습니다.

    하위 호환성

    현재 설계는 몇 가지 중요한 방식으로 호환성을 유지합니다.

    • Borg 기반 상태 공유 동작을 위한 PluginManager가 여전히 존재합니다.
    • TenantPluginManager는 PluginManager와 같은 공개 생명주기 및 훅 호출 API를 유지합니다.
    • 인자 없는 get_plugin_manager()는 여전히 전역 __global__ 매니저를 반환합니다.
    • 컨텍스트를 인식하지 않는 호출 지점은 계속 전역 매니저로 동작합니다.

    바뀐 것은 연결 구조입니다. 이제 시스템은 공유 매니저 인스턴스 하나 대신 팩토리를 거쳐 플러그인에 접근합니다.

    • 플러그인은 시작 시 YAML에 한 번 선언 — YAML이 정식 플러그인 레지스트리
    • 컨텍스트별 오버라이드는 매니저 생성 시점에 가져옴 — get_config_from_db를 통해 가져오며, 서브클래스로 DB에 연결
    • 공유 기본 설정 하나에, 선택적으로 컨텍스트별 오버라이드를 병합 — 오버라이드 키가 우선하며, 알 수 없는 플러그인은 무시

    이것이 코드가 구현한 현재 아키텍처이며, 모든 요청 경로가 플러그인 설정이 내부적으로 어떻게 저장되는지 이해할 필요는 없습니다.
